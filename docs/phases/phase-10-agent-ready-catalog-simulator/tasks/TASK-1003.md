# TASK-1003 — LLM Context Tabs Across Active Engineering Pages

Status: **DONE**
Linear: [ZFA-58](https://linear.app/recruit-verse/issue/ZFA-58)

Phase: **10 — Agent-Ready Engineering & Full Catalog Go Simulation**

## Objective
Add an LLM Context tab to every active engineering page.

## Initial coverage
Factory overview/designer, PLC overview/hardware/I-O/program/runtime/export, devices, catalog-backed configuration, wiring/connections, process modules, simulation, events/live state, topology/3D where useful, gateway/edge configuration and engineering export.

## Acceptance criteria
- Each active page exposes only context relevant to that page.
- Values and relationships match the normal UI.
- Sensitive secrets are never exposed.
- Context includes validation errors and available next actions.

## Decisions (owner, 2026-10-09)
- **Coverage:** every engineering page. Left out: the home redirect, the LLM Index itself, the printable export report, and the create/edit factory forms (their decisions are in the overview's context).
- **Delivery:** three PRs under this one task. PR A: the nine PLC screens. PR B: the factory-level pages (runtime, simulator, scenarios, live tags, events, gateways, process modules, module editor). PR C: designer, topology, 3D, the device screens, the new-PLC form, the catalog and the Factories list. The task is DONE after PR C.

## PR A — the PLC screens
### Implementation
- `components/plc/stored-plc-shell.tsx` takes `llmContext` and renders the panel after the screen's content: one place for all nine screens.
- `lib/agent/contexts/plc.ts`: `buildPlcContext({ factory, view, section, … })`. The common part comes from the `PlcConfigurationView` every screen loads: model and catalog record, architecture, runtime state, role, I/O occupancy and mapping versions; the wired devices with their wires, ports and rack modules as objects; "X is wired to PLC" with terminal → point as relationships; free channels per bank and free slots as capacity; the screen list, designer, simulator, live tags and events as navigation, without the screen itself. Each screen adds its own data, actions and issues: installable modules and the install/remove actions (hardware); the editor's starting point, stored versions, located variables and Check / Save version / Save & deploy, the last gated on a runtime (program); the versions with status, a failed version as an issue, Use for next start and Deploy now gated on a runtime (versions); the real state, container, Modbus TCP endpoint, programs, the last five events and Start, Deploy, Restart, Stop, Remove, Refresh state, each with its warning (runtime); peers, links with their health and a changed-since-deployed warning (communication); the export revision, mappings, program, snapshot and every download (export). Connections and I/O mapping say they are read-only and point to the designer.
- Kept out of the context: a link's server host and port (the page shows them; the context names the peer), the runtime's service name, container ids, ports of the management API, tokens.
- `lib/agent/contexts/registry.ts` adds `plc`, `program`, `plc-communication` and `export`; the LLM Index names them.
- Docs: `docs/design.md`, `docs/api-contract.md`, `docs/status.md`.

## PR B — the factory-level screens
### Implementation
- One builder per screen, each taking the view models the screen already loads: `buildFactoryRuntimeContext`, `buildSimulatorContext`, `buildScenariosContext`, `buildLiveTagsContext` and `buildEventsContext` in `lib/agent/contexts/factory-operations.ts`; `buildGatewaysContext`, `buildModulesContext` and `buildModuleEditorContext` in `lib/agent/contexts/factory-engineering.ts`. Each screen renders the panel as the last child of its content.
- Runtime: the PLCs with their state and a link to each runtime, the simulation, Docker, the start and stop order, Start factory gated on Docker and a PLC, Stop factory with its warning, a running plant as a decision, and PLCs running without the simulation as an issue. Simulator: every simulated device with the tags its commands come from and its feedback goes to, faults (with the active ones as issues), bad quality, the blocker, the PLC endpoints and the skipped devices; inject, clear and reset. Scenarios: overrides out of AUTO, recorded runs, the example scenario's command and expected tags, a silent service. Live tags: the first sixty tags with value, quality, authority and address, writable and stale counts, the write action with its warning, `?plc=` narrowing. Events: active alarms as validation items with their state, the first forty events with family and device, the filters in force, counts by severity, retention, acknowledging as a decision. Gateways: devices, each connection with endpoint, clients, requests and refusals, registers with access, unmapped tags, the port range and the next free port, a failed endpoint as an issue, host and writable tags as decisions. Process modules: each module with type, state, device count and issues, each type with its process model; the editor: devices by role, the I/O registry row by row with bindings and issues, interlocks, test inputs with their mode, the bridge state, role and signal capacity, and the open questions.
- Kept out: nothing an agent could use to bypass the UI; endpoints and ports are what the pages show.
- `lib/agent/contexts/registry.ts` adds `runtime`, `simulation`, `tags`, `events`, `gateways`, `modules`.
- Docs: `docs/design.md`, `docs/api-contract.md`, `docs/status.md`.

### Evidence (2026-10-10)
- **Builders** (`lib/agent/contexts/factory-pages.test.ts`): the runtime context on a stopped factory (Start as a warning, "Start the plant?"), with Docker down and no PLC (the two issues, Start disabled, no decision), and degraded with a faulted PLC and a failing simulation cycle; the simulator with a faulted, bad-quality valve and its wired signals, and stopped with a blocker and a not-ready endpoint; scenarios with an override, a run and the example tags, and with a silent service; live tags narrowed to a PLC with a writable and a stale tag, and idle without a monitored PLC; events with an active critical alarm, a filtered list, counts and retention; gateways with a failed endpoint, a writable register and an unmapped tag; the modules list with an incomplete module and a type without a process model; the editor with an empty required role, an unbound required signal, a bound one, a PLC in use and a service note. Every document has the ten sections and never links to its own route; the registry and the LLM Index agree.
- **Browser** (the owner's `next dev`, the running Pump Station Demo, headless Chromium): the runtime, simulator, scenarios, live tags, events, gateways and process modules screens each carry a panel with the right page, area, actions and decisions. The runtime panel found a real condition: "PLCs run without the device simulation" (the demo's PLC runs while its simulation is stopped), so the simulator panel offers "Start the simulation?". The demo has no process module, so the editor's panel is covered by its test. Opened on the simulator, the ten sections render under the device cards.
- **Gates** (a clean worktree of this branch): `npx prettier --check .`, `npm run lint`, `npx tsc --noEmit` and `npm run build` are clean. `TEST_DOCKER=1 npm test`: 105 files, 1089 tests passed. Nothing left in Docker.

## PR C — the design screens
### Implementation
- `lib/agent/contexts/design-pages.ts`: `buildTopologyContext` (designer and topology), `buildView3dContext`, `buildDeviceContext` (the five device screens, through `DeviceShell`, which takes `llmContext` like `StoredPlcShell`), `buildNewPlcContext`, `buildCatalogContext` and `buildFactoriesContext`. Each takes the view models its screen already loads.
- Designer and topology: nodes with model, role, state and whether they are placed; edges as sentences ("PLC-01 is wired to VFD-01, 7 wires", with each wire and its tag; "VFD-01 drives MOTOR-01"); the palette by category as capacity; a PLC missing, loose and faulted devices as issues; the canvas actions and the connection rules; which model and which relationship to ask for; a running factory as a decision. The panel comes after the canvas as the last child of the shell; closed, it leaves the canvas its height. 3D: devices with their asset or generic shape, the connections, visualization only. Device screens: the model with its catalog link, wires, tags with their PLC and register, ports, parameters with the save warning when they are applied, the record-only note when they are not, and the device's other screens as navigation. New PLC: the models offered with I/O and ports, the existing PLCs, the suggested name, the model, architecture and role decisions, the empty catalog as an issue. Catalog: totals, the category filter, the selected model with source, verification, control capability, built-in I/O, rack and modules, a PLC's compatible peripherals terminal by terminal, a failed asset as an issue, the vendor-or-generic decision. Factories: each factory with state, subnet and last event, Docker, the subnets in use, degraded factories and an unreachable engine as issues, the first-run case.
- `lib/agent/contexts/registry.ts` now names every area of the LLM Index except the index itself.
- Docs: `docs/design.md`, `docs/api-contract.md`, `docs/status.md`.

## Acceptance
- Each active page exposes only its own context: one builder per page from the page's own view models, nothing shared but the shape.
- Values and relationships match the UI: the builders take the rendered view models, and the page tests assert the same facts the pages show.
- No secrets: no container id, management port, token or password reaches a document; link hosts and ports stay on their pages.
- Every document carries validation issues and the available actions; an empty section says "None.".
