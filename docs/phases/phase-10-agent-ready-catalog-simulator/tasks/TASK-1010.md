# TASK-1010 — Catalog Device Capability & Behavior Schema

Status: **DONE** (2026-10-11)
Linear: [ZFA-65](https://linear.app/recruit-verse/issue/ZFA-65)

Phase: **10 — Agent-Ready Engineering & Full Catalog Go Simulation**

## Objective
Define the machine-readable behavior contract every simulatable catalog model uses.

## Schema concepts
Commands, feedback, parameters, units, ranges, states, timing, faults, latching/reset rules, quality, protocol behavior, relationship requirements and fidelity/coverage state.

## Acceptance criteria
- Catalog validation rejects impossible/incomplete simulator metadata.
- Generic and vendor-specific facts are clearly separated.
- A vendor profile never implies firmware emulation merely because its physical model exists.

## Prerequisites
- TASK-1009 (DONE): the runtime's behaviour profiles describe themselves over `GET /v1/profiles`; `DEVICE_PROFILES` names a profile per simulated type.
- TASK-301/307/308: the catalog schema, its rules and provenance (`lib/catalog/schema.ts`), terminals with `simulatorSignal`, capabilities per model.

## Decisions (2026-10-11; ADR-0026)
- **One behaviour contract, in the domain.** `lib/domain/behavior-contract.ts` is the machine-readable contract of every behaviour profile: commands and feedback (signals with direction, kind, unit, range), parameters (kind, unit, default, bounds, role: rating, timing, limit, initial, source), states, faults with their reset rule and effect on quality, links by role with the relationship they come from, protocol behaviour, forcing, and the fidelity notes (approximations and what is not modelled). The Go runtime describes the same facts (`parameterSchema` joins the profile description) and the parity test holds the two together.
- **Every catalog model declares its simulation.** A `simulation` block is mandatory per model: `NOT_SIMULATABLE` with the reason, or `GENERIC` / `PARTIAL` / `FULL` with the profile and version, the supported faults, parameter values and, for PARTIAL and FULL, the declared model-specific features and whether each is implemented. The catalog rules refuse what is impossible or incomplete: a simulated model whose runtime is not the device simulator (and the reverse), a profile the model's category does not have, an unknown profile or version, a fault or parameter the profile does not have, a value outside the profile's bounds, a terminal naming a signal of a model that is not simulated, FULL without every feature implemented, PARTIAL without a mix.
- **Generic and vendor facts stay apart.** A generic model is `GENERIC` or `NOT_SIMULATABLE`: it has no model-specific features. A vendor model may be `GENERIC` (category behaviour only, no vendor claim); `PARTIAL` or `FULL`, or any parameter value, is a model-specific fact and needs the model's `VERIFIED` provenance. Coverage is a Z-Factory statement about a behaviour model; no value of it means vendor firmware, and a programmable controller is `NOT_SIMULATABLE` as a device because its program runs on the OpenPLC adapter.
- **Persisted and shown.** `DeviceModel` gains `simulationCoverage`, `simulationProfile`, `simulationProfileVersion` and `simulationJson` (forward migration `catalog_simulation_coverage`); catalog parameter values become the model-level `SimulationProfile` the simulator already reads; the catalog screen and its LLM Context show the coverage with the words "behaviour model, not vendor firmware".

## Acceptance
- Catalog validation rejects impossible/incomplete simulator metadata: `parseCatalog` refuses a simulated model without the device simulator as runtime and the reverse, a missing block (the shape is mandatory), an unknown profile or version, a profile of another category, a fault or parameter the profile lacks, a value outside the profile's bounds, a terminal signal on a model that is not simulated, `FULL` with an unimplemented feature, `PARTIAL` without a mix, a feature declared twice; `lib/catalog/catalog.test.ts` → "simulation decision rules".
- Generic and vendor-specific facts are clearly separated: a generic model is `GENERIC` or `NOT_SIMULATABLE` and cannot declare features; a vendor model's `PARTIAL` or `FULL` coverage or parameter values need its `VERIFIED` provenance; the shipped catalog claims nothing model-specific; "keeps generic and vendor facts apart" in the same test.
- A vendor profile never implies firmware emulation merely because its physical model exists: coverage is a property of a behaviour model and the catalog screen and LLM Context say "a behaviour model, not vendor firmware" with every simulated coverage; the four vendor PLCs are `NOT_SIMULATABLE` with the OpenPLC reason, and a PLC claiming a profile is refused ("ties the coverage to the runtime").

## Remaining limitations
- No model claims `PARTIAL` or `FULL` yet: the behaviour library has no model-specific behaviour until TASK-1011, and the per-fact provenance of vendor parameters is TASK-1012. The rules and the storage are in place for both.
- `protocol` is `NONE` for every shipped profile; the Modbus device side and its register contract are TASK-1013, and the models that wait for it are `NOT_SIMULATABLE` with that reason.
- The server's simulator still selects a device's behaviour by its category's `simulatorType`; the catalog rules guarantee the model's declared profile is that type, and TASK-1015 switches the selection to the stored `simulationProfile` when factories move to the runtime.
- The coverage report over every model (TASK-1016) is not written yet; the columns and the contract it reads are.
