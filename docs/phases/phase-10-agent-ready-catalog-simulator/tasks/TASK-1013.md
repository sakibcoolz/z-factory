# TASK-1013 — Protocol/Register-Controlled Device Simulation

Status: **DONE** (2026-10-12)
Linear: [ZFA-68](https://linear.app/recruit-verse/issue/ZFA-68)

Phase: **10 — Agent-Ready Engineering & Full Catalog Go Simulation**

## Objective
Simulate protocol-controlled devices and register behavior where an authoritative Z-Factory mapping exists.

## Scope
Start with existing supported industrial transports such as Modbus TCP where appropriate. Keep protocol adapters extensible.

## Acceptance criteria
- Protocol simulation uses declared mappings only.
- Unknown vendor register maps are not guessed.
- Reads/writes obey the device behavior model, range rules and writable permissions.

## Prerequisites
- TASK-1009 (DONE): the runtime, its factory contract and the device simulation.
- TASK-1010 (DONE): the behaviour contract, with `protocol` reserved on every profile for this task.
- TASK-1012 (DONE): the per-fact source rule a vendor's register map would fall under.
- TASK-203/501 (DONE): the server's Modbus vocabulary (areas, data types, roles, conventions) and its Modbus TCP server for gateway endpoints, whose request rules this task mirrors on the device side.

## Decisions (agent, 2026-10-12; for the owner to confirm; ADR-0027)
- **A register map is declared, in the contract, and never derived.** `lib/domain/register-maps.ts` states each map: the profile, and per register the signal, area, address, data type, scale, offset, unit, access, role and the signal's range for a writable register. The area and the access follow from the signal's direction and kind, so feedback can never be writable; the rules are checked on the server and at registration in the runtime, and the parity test compares the two declarations field by field. One generic map ships, `VFD_MODBUS_TCP` v1 (commands as coils, the setpoint in 0.1 Hz, feedback as discrete inputs and input registers in tenths). A vendor's map is catalog data with its provenance and is not declared: the catalog refuses a model naming a map that is not declared.
- **The runtime serves the maps, one Modbus TCP listener per factory.** A factory configuration asks for a listener (`modbusTcp: { port }`, 0 for any free port of the runtime's range); a device names its protocol, unit id and map. The listener is Go's standard library only (`internal/modbus`), opened on `PROCESS_SIM_MODBUS_BIND` when the factory loads and closed when it is unloaded or replaced. Reads give commands as last written and feedback as produced, scaled; writes set the behaviour's inputs only on writable registers within range (a bound naming a parameter is resolved against the device's effective parameters), applied whole or not at all; an unmapped address or a write to a read-only area answers `02`, a value out of range `03`, an unknown unit id `0A`, as the gateway endpoints answer. Writes and refusals are events, refusals rate-limited per address.
- **The behaviour does not change.** The Modbus drive is the VFD profile behind the map; a write over Modbus and a PLC output on a terminal set the same input. The PLC stays the authority; the runtime never writes a PLC output.
- **The catalog names the map.** `protocol` on a simulated block, and `runtimeOnly` (profile, version, protocol) on a `NOT_SIMULATABLE` model the runtime runs, so TASK-1015 can switch models over by data; the four library models of TASK-1011 are migrated to `runtimeOnly`. A protocol model has a port for its protocol. The import writes the map into `ProtocolRegisterDefinition`; the screen and the LLM Context show it.
- **Honest scope.** The path from a PLC container to a listener (the runtime binds loopback; PLC containers live on factory networks; the OpenPLC master configuration names only PLC links) belongs to TASK-1015 with the switch of factories to the runtime. A remote I/O station needs a profile of its own (channels, not a behaviour) and a gateway stands for an external device (ADR-0013): both stay `NOT_SIMULATABLE` and say so, instead of "registers are coming".

## Acceptance
- Protocol simulation uses declared mappings only: a device is served only with a map the runtime declares (`register-map`), of its own profile and version (`register-map-profile`, `register-map-version`); a read or write of an address the map does not name answers exception `02` before the device is touched; the catalog refuses a model naming an undeclared map.
- Unknown vendor register maps are not guessed: no vendor map is declared; the one map is Z-Factory's generic declaration for the generic model and says so on the screen and in the LLM Context; a vendor map would need its source per fact (TASK-1012).
- Reads/writes obey the device behaviour model, range rules and writable permissions: a write lands on the profile's inputs and the behaviour reacts at the next step; only a command or setpoint is writable (the area follows the direction, feedback is read-only by construction); a setpoint outside the signal's range, resolved against the device's parameters, answers `03`; a multi-register write is applied whole or not at all.

## Remaining limitations
- A PLC container cannot reach a listener yet: the runtime binds loopback and the PLC's Modbus master configuration names only PLC links. TASK-1015 decides the network path and configures the master for a device; the Modbus drive stays `NOT_SIMULATABLE` with that reason.
- Only single-word registers (BOOL, UINT16, INT16) are served; no profile signal needs 32-bit values yet.
- Modbus TCP is the one protocol kind; the map's `protocol`, the listener and the catalog rule are keyed by kind for the next one.
- No remote I/O profile; no vendor register map.
