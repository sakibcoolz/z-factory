# TASK-1007 — Agent-Readable Validation & Error Explanations

Status: **DONE**
Linear: [ZFA-62](https://linear.app/recruit-verse/issue/ZFA-62)

Phase: **10 — Agent-Ready Engineering & Full Catalog Go Simulation**

## Objective
Make engineering validation results specific enough for a browser agent to explain and correct.

## Required fields
Rule/code, object/source, destination where relevant, expected condition, actual condition and safe remediation guidance.

## Acceptance criteria
- Validation messages identify the failing engineering rule.
- Browser agents can distinguish fixable configuration errors from unsupported operations.
- Human UI and LLM Context use the same validation source.

## Decisions
- Engineering rules first (owner, 2026-10-11): the rules an agent meets while designing (wiring, PLC architecture and configuration, tags and addresses, process modules, gateways and links, factory configuration, device parameters, export, edge and catalog) get a full entry: kind, what the rule expects, what to do. Runtime, Docker, simulator, asset-authoring and compiler rules get a generic explanation from their code and family now, and their own entries in a follow-up task.
- Four kinds, so an agent can tell what to do with a refusal: `fixable` (change the configuration and retry), `unsupported` (the product does not do this; choose another way), `state` (not now; start, stop, remove or bind something first), `unavailable` (a host, service or runtime did not answer; retry or see the Runtime page).
- One source for people and agents: the same `ValidationExplanation` is rendered under the human message and carried by the LLM Context, so the two can never disagree.

## Implementation
- `lib/domain/validation-explanations.ts` (pure, importable by components): `RULE_EXPLANATIONS`, 101 engineering rules with kind, area of the LLM Index, expected condition and remediation; `REFUSAL_KINDS`; `explainDomainError(error)` turns a `DomainError` into a `ValidationExplanation { code, rule, kind, expected?, actual, remediation, area?, field?, object?, destination?, facts }`, reading the field, the object (terminal, tag, device, …) and the destination (channel, PLC, conflicting tag, …) from the error's details and keeping the rest as facts; a rule without an entry gets a generic explanation from its code and its family (`runtime-`, `docker-`, `simulation-`, `asset-`, `program-` …). Server output (`log`, `stderr`, `stack`, `cause`, …) never becomes a fact; a fact is cut at 200 characters. `explainRule(rule, actual, extra)` explains a rule met in stored state (a module issue, an I/O registry row); `explanationLine()` is the one-line form for Markdown.
- `components/ui/refusal.tsx`: `RefusalExplanation`, the rule or code, a kind pill, object and destination, "Expected:", "Do:" and the facts; `data-llm-refusal` (rule or code) and `data-llm-refusal-kind` for agents.
- Every refusal the human UI shows carries it: `OperationState.explanation` (`toOperationState`, rendered by `OperationForm` under the message: runtime, program, versions, simulator, scene and live actions), the designer's `CanvasResult` (the canvas notice and the wiring editor), `PairWiringView.rules` (the rule behind every refused pair of endpoints, so the wiring editor explains a refusal before a wire is tried), `FactoryFormState.explanation` and `DeleteFactoryState.explanation` (the factory form and the delete confirmation).
- The LLM Context: `LlmContextItem.explanation`; the panel renders it, the JSON carries it, the Markdown appends `explanationLine()`. The module screens and the module editor attach it to module issues and to invalid I/O registry rows.
- The LLM Index: a "How a refusal reads" section with the kinds and the table of rules (page and Markdown).
- Tests: `lib/domain/validation-explanations.test.ts` walks the engineering sources (`rule: "x"`, `refusal("x"` and `"wire-x" as const`) so no rule they raise is without an entry, and checks every entry names a rule the code raises, a known kind and an area of the index; explanation of known, unknown and rule-less errors, facts, object and destination; `components/ui/refusal.test.tsx`; the operation form, wiring editor, panel, Markdown, index and module context tests; the integration tests that compared a refusal's exact shape now expect the explanation too (`refused(message)`).
- Docs: `docs/design.md`, `docs/api-contract.md`, `docs/status.md`.

## Acceptance
- Validation messages identify the failing engineering rule: every refusal names its rule (or its code when the error has none), on the page and in the LLM Context.
- Browser agents can distinguish fixable configuration errors from unsupported operations: the kind (`fixable`, `unsupported`, `state`, `unavailable`) is on every explanation, as a pill and as `data-llm-refusal-kind`; the index defines the four.
- Human UI and LLM Context use the same validation source: both render the `ValidationExplanation` of `lib/domain/validation-explanations.ts`.

## Remaining limitations
- Runtime, Docker, simulator, asset-authoring and compiler rules have a generic explanation (kind and remediation from the code and the rule's family), not their own entry: a follow-up task.
- The wiring editor explains the refusal of a chosen pair; the designer's drag-to-connect still shows the server's message with its explanation only after the attempt.
