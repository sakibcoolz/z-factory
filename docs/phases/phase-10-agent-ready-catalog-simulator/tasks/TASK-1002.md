# TASK-1002 — Reusable Page-Level LLM Context Framework

Status: **DONE**
Linear: [ZFA-57](https://linear.app/recruit-verse/issue/ZFA-57)

Phase: **10 — Agent-Ready Engineering & Full Catalog Go Simulation**

## Objective
Create one reusable LLM Context pattern for all active engineering pages.

## Required sections
- Page identity
- Current context
- Available objects/resources
- Current relationships
- Capacity/availability
- Validation state
- Available user actions
- Engineering constraints
- Missing decisions / recommended questions
- Navigation guidance

## Acceptance criteria
- All pages use the same semantic structure.
- Context is generated from current application data, not stale documentation.
- The component remains readable to humans while being predictable for browser agents.

## Decisions (owner, 2026-10-09)
- The LLM Context is a collapsible panel at the end of every page's content: closed for people, always in the DOM for agents. No page needs client state or a query parameter.
- The factory overview proves the framework in this task; TASK-1003 rolls it out.

## Implementation
- `lib/agent/llm-context.ts`: `LlmContextDocument` (version 1) with the ten required sections in a fixed order; `createLlmContext(identity, parts)` fills empty sections and derives the validation status from its items; `renderLlmContextMarkdown`. Items carry a label, an optional value, a route when there is one to open, a sentence of detail and a tone.
- `components/agent/llm-context.tsx`: `LlmContextPanel`, a `details[data-llm-context][data-llm-page][data-llm-version]`, one `section[data-llm-section]` per section with its title, "None." where a section is empty, a status pill for validation, and the document once more in `script[data-llm-context-json]`.
- `lib/agent/contexts/factory-overview.ts`: `buildFactoryOverviewContext` from the factory view, the device tree the page renders, the PLC summaries and the Docker status. Objects and relationships come from the tree; capacity from channel occupancy; validation from Docker, the runtime state, faulted and unconnected devices and PLCs without a program; actions follow the page's buttons (delete only while stopped); decisions name what to ask the user (which PLC, what the plant should do, control logic, a running plant).
- `listFactoryPlcSummaries` in `lib/services/plc-config-service.ts` with `plcConfigRepository.listFactoryPlcProfiles`: per PLC, whether a program is selected, the I/O mapping version and channel occupancy. A read model; no schema change.
- `lib/agent/contexts/registry.ts`: the areas with a panel. The LLM Index derives its "LLM Context" column from it (the manual flags of TASK-1001 are gone).
- The factory overview page renders the panel after its content.
- Docs: `docs/design.md`, `docs/api-contract.md`, `docs/architecture.md`, `docs/status.md`.

## Limitations
- Only the factory overview has a panel; TASK-1003 adds the rest, one builder per page, and TASK-1004 the generated navigation index. Relationships here are the device tree's (which device hangs under which), not the typed relationships (DRIVES, MEASURES) the designer stores; a page-specific builder can say more.
- No per-page text route; the JSON copy inside the page serves agents that parse rather than read. Revisit after TASK-1008 if agents need to fetch it.
