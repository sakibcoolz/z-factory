# TASK-1012 — Vendor Catalog Model to Simulation-Profile Mapping

Status: **DONE** (2026-10-12)
Linear: [ZFA-67](https://linear.app/recruit-verse/issue/ZFA-67)

Phase: **10 — Agent-Ready Engineering & Full Catalog Go Simulation**

## Objective
Map catalog vendor models to safe documented simulation profiles when no approved vendor runtime/emulator is available.

## Rules
- Reuse generic category behavior where only generic behavior is known.
- Add model-specific parameters only from authoritative sources.
- Store provenance for model-specific behavior facts.
- Never copy/provide proprietary firmware.

## Acceptance criteria
- Every vendor catalog model has an explicit runtime/simulation support decision.
- Mapping does not overstate vendor fidelity.

## Prerequisites
- TASK-1010 (DONE): the behaviour contract and the mandatory `simulation` block of every catalog model, with the rule that a vendor model's model-specific behaviour needs `VERIFIED` provenance (ADR-0026, decision 4, which left the per-fact source to this task).
- TASK-1011 (DONE): the behaviour library; the runtime-only rule a vendor model of those categories falls under until TASK-1015.
- TASK-301: vendor records with provenance (`lib/catalog/vendor/`), `docs/references/plc-source-policy.md`.

## Decisions (agent, 2026-10-12; for the owner to confirm)
- **A vendor model runs the generic profile of its category.** No vendor runtime or emulator exists for any catalog device, so the mapping is: programmable controller → `OPENPLC`, `NOT_SIMULATABLE` as a device; a category whose profile the server's simulator runs → `DEVICE_SIM` on that profile, `GENERIC` with no claim or `PARTIAL`/`FULL` with declared features; a runtime-only category → `NOT_SIMULATABLE` until TASK-1015, like its generic model; a protocol device → TASK-1013. The decision tree is in `docs/device-catalog.md` → Vendor models on behaviour profiles. Nothing new is modelled: the profiles are TASK-1009's and TASK-1011's.
- **A source per fact.** `simulation.sources` of a vendor model has one entry per parameter value (`parameter:<key>`), declared feature (`feature:<KEY>`) and supported fault (`fault:<CODE>`), each with the place in the manual (`reference`: parameter, table, page) and, when the vendor's meaning is not the profile's exactly, a `note` with the approximation. A model may list further manufacturer documents (`documents`, by key) and a source may name one; without one the model's verification source applies. The catalog refuses an unsourced fact, a source for an undeclared fact, a source naming an unlisted document, and any source or document on a generic model. A supported fault counts as a model-specific fact: listing it says the drive has such a trip.
- **Factory configuration, not reprogramming.** A vendor model's terminals carry a profile signal only where the manual's factory assignment gives them that function; a programmable terminal without one carries none, and so does a terminal whose factory function is the inverse of a profile signal (a "ready / no fault" relay), with the reason in its notes. Parameter values are the manual's factory settings, never tuned values; a parameter the profile does not have is not recorded.
- **No firmware.** A model the device simulator executes may not be `FIRMWARE_DEPLOYABLE`; the catalog refuses it. Nothing of Z-Factory runs, ships or imitates vendor firmware, and the coverage sentence keeps saying so.
- **Two drives as the first mapped models**, read from manufacturer manuals the way the PLC records were: the Rockwell PowerFlex 525 (25B-D010N104; 520-UM001O-EN-E, September 2025) and the Schneider Altivar Machine ATV320 (ATV320U07N4C; installation manual NVE41289.09 and programming manual NVE41295.06, 04/2025). Both `PARTIAL` on `VFD` v1: the profile implements their linear ramps, reversal and the two trips; S-ramps, DC braking, current limitation, automatic restart, flying start and the built-in PID regulator are declared and not implemented. The nine declared features are one Z-Factory list (`DRIVE_FEATURES`), so two drives on the same profile are compared on the same terms. No storage change: the resolved sources live in the model's `simulationJson`, and a vendor fault's reference in `DeviceFaultDefinition.description`.

## Implementation
- `lib/catalog/schema.ts`: `documents` per model; `sources` in the simulated block (`factSourceSchema`: document key, reference, note); `FACT_KINDS`, `factKey`, `checkFactSources`, `resolveFactSource`; a supported fault is model-specific; `FIRMWARE_DEPLOYABLE` refused on a `DEVICE_SIM` model; a generic model refused documents and sources.
- `lib/catalog/ingest.ts`: `simulationJson` stores the block with every source resolved to its document; `DeviceFaultDefinition.description` carries a vendor fault's reference.

## Acceptance
- Every vendor catalog model has an explicit runtime/simulation support decision: the six vendor models each carry `runtimeSupport` and a `simulation` block (four PLCs `OPENPLC` / `NOT_SIMULATABLE` as program hosts, two drives `DEVICE_SIM` / `PARTIAL` on `VFD` v1), checked by `parseCatalog` and the shipped-catalog tests; the decision tree for the next vendor model is documented.
- Mapping does not overstate vendor fidelity: coverage is `PARTIAL` with the absent behaviours declared, the values are the manuals' factory settings with their page, the approximations (HSP against tFr, ACC/DEC against FrS, one overcurrent trip) are written in the facts' notes, the terminals carry only factory assignments, inverse relays carry nothing, and the screen and the LLM Context say "a behaviour model, not vendor firmware" beside every value and its source.

## Remaining limitations
- Two vendor devices are mapped; the mapping of further vendor models follows the same rules record by record, each read from its manual.
- A vendor model's fault relay (ready / no-fault contact) carries no profile signal because the wiring model has no inverted signal; the drives report `faulted` through no terminal. A follow-up may add a per-terminal inversion.
- The PowerFlex 525's terminal-block control applies while its terminal 07 ("Spd + Strt 2") is energized, as the record's notes say; the profile does not model the drive's source selection.
- The vendor drives wait, like the generic ones, for TASK-1015 to be selected by their stored profile at runtime; the server's simulator still selects by category type, which the catalog rules keep equal.
