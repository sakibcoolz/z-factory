# TASK-1008 — Browser-Agent End-to-End Engineering Validation

Status: **DONE**
Linear: [ZFA-63](https://linear.app/recruit-verse/issue/ZFA-63)

Phase: **10 — Agent-Ready Engineering & Full Catalog Go Simulation**

## Objective
Prove a browser-based agent can discover, recommend and apply an engineering change using only visible Z-Factory UI/context.

## Reference scenario
Create a tank, level sensor and pump; select compatible catalog models; confirm PLC capacity; create approved devices; wire compatible endpoints; validate; report the resulting design.

## Acceptance criteria
- No MCP/private database interface is used.
- Agent starts from Global LLM Index.
- Agent uses page-level LLM Context as it navigates.
- User decisions are requested where required.
- Final configuration passes normal Z-Factory validation.

## Decisions (2026-10-11)
- **A scripted agent, in the test suite.** The proof is a deterministic agent (`test/browser-agent/browser-agent.ts`) that drives a real Chromium over the DevTools protocol and knows the application only from what its pages show: the LLM Index's DOM, each page's LLM Context JSON (`script[data-llm-context-json]`), the normal controls. It imports nothing of Z-Factory, and the first test enforces that. A model-driven agent reads the same attributes and the same JSON; the scripted one makes the proof repeatable and fails loudly where a page falls short.
- **The user is a script.** Every decision a context marks `confirm: required` is put to a `User`; in the test, a table of answers. A question without an answer fails the run, so the set of questions the agent needs is asserted, not assumed. An optional decision with a default (the channel) is applied and recorded as such.
- **The scenario in product terms.** A tank is a process module of type Tank (profile LEVEL), whose required roles are a level transmitter and an inlet valve. A pump needs a motor, and a motor a drive, so the pump is driven by a motor from a VFD; the drive is wired to the PLC. One compact PLC: the generic RTU (8 DI, 4 DO, 4 AI). Wires: transmitter OUT → AI, valve Y1 → DO, VFD RUN → DO, VFD RUNNING → DI. The module takes the transmitter and the valve in their roles.
- **The server is the product.** `next start` of the production build, on the integration-test database with a local owner (`test/browser-agent/app-server.ts`); the agent reaches it over HTTP only. Gate `TEST_BROWSER=1`, browser from `CHROME_BIN` or the Playwright cache, `TEST_BROWSER_OUT` for screenshots and the agent's report; `npm run build` comes first.
- **Gaps the run found are closed when they are agent-readiness gaps, and reported when they are product scope.** Closed: connecting two devices was a drag only (the inspector gained **Connect to**); the module editor's context asked for roles of other profiles. Reported, not closed: no page creates the program-driven (%M) tags a process module's signals bind to.

## Implementation
- `components/canvas/topology-inspector.tsx`: **Connect to** on the selected device: a list of the factory's other devices and a Connect button, calling the canvas's `link` as a drag between handles does (the relationship question or the pin-to-pin editor follows). `components/canvas/topology-canvas.tsx` passes `onConnect`. For keyboard users as much as for agents.
- `lib/agent/contexts/factory-engineering.ts`: the module editor's empty-role decisions and role capacity come from the module's own roles (its profile), as the page shows them, not from every role of the type.
- `test/browser-agent/cdp.ts`: a minimal DevTools driver (`findChromium`, `Browser.launch`, `Page.goto / eval / waitFor / screenshot / close`); every tab a run opens is closed.
- `test/browser-agent/app-server.ts`: `next start` on a free port with `DATABASE_URL` = the test database, `LOCAL_OWNER_ID`, a non-production `RUNTIME_SECRET`; waits for `/llm-index.md`.
- `test/browser-agent/browser-agent.ts`: the agent. Reads the index (sections, areas, workflow) and follows the Factories area's link; takes "New factory" from the list's context actions; asks name and subnet (the form has no context, the index's rules apply); reads the overview's "Which PLC?" decision and its "Add compact PLC" action; chooses the PLC model from the form's radios after asking; reads capacity from the PLC context and confirms 1 AI, 2 DO, 1 DI before wiring; takes the designer link from the context; adds each device with the palette's **Add** button after asking the model; connects with **Connect to**, answers the relationship dialog through the user, and wires in the pin-to-pin editor, trying each point of the wanted type until one takes the terminal (the channel default applied and recorded); creates the module from the modules page's form after asking type, profile and name; fills every empty required role the context lists; for each required unbound signal reads the picker and, when every candidate is refused, records the refusals as blocked work; re-reads the designer, the module, the overview and the I/O mapping for their validation; returns a report (pages, questions and answers, defaults, changes, capacity, validation, the design, what was not possible) as data and as Markdown.
- `test/browser-agent/browser-agent.test.ts`: the isolation test (always) and the end-to-end run (`TEST_BROWSER=1`): seeds the catalog and the module types, starts the server and the browser, runs the agent once, then asserts the index came first, every page but the index and the factory form had a context, the required questions were asked with the page's choices, only the channel default was applied, capacity was confirmed, the design pages report `ok`, the stored design matches (six devices, five connections, four tags, the module's roles filled), and the two unbindable signals are reported with their reason.
- Tests: `components/canvas/topology.test.tsx` (Connect to in the inspector; the relationship dialog from the canvas), `lib/agent/contexts/factory-pages.test.ts` (a required role of another profile is neither a decision nor a capacity line).
- Docs: `docs/testing.md`, `docs/design.md`, `docs/architecture.md`, `docs/bootstrap.md`, `.env.example`, `docs/status.md`.

## Acceptance
- No MCP/private database interface is used: the agent's modules import only Node and each other; it reaches the application over HTTP through Chromium; the test enforces the imports.
- Agent starts from Global LLM Index: the first page is `/llm-index`; the agent reads its sections, areas and workflow and follows the Factories area's link.
- Agent uses page-level LLM Context as it navigates: every page after the index, except the factory form (which has none by the TASK-1003 decision), is read through its context: actions and navigation give the links, capacity the free channels, decisions the questions, validation the result.
- User decisions are requested where required: thirteen questions, each from a required decision of a context or from the index's rules, each with the page's choices; the one optional decision (the channel) is applied with its default and recorded.
- Final configuration passes normal Z-Factory validation: the designer, the factory overview and the I/O mapping report `ok`; the services agree. The process module's two required signals cannot be bound through any page (see Remaining limitations), which the agent reports instead of working around.

## Remaining limitations
- **No page creates program tags.** A process module's signal binds only to a tag the PLC program drives (a %M address, not a wired device's tag), and `createTag` is reached only by the demo. Until a tag screen exists (or tags come from the program's located variables), a hand-built module stays "required unbound". Follow-up task proposed.
- The factory form has no LLM Context (TASK-1003 decision); the agent asks the name and the subnet from the index's rules.
- The agent is scripted: it proves the pages carry what an agent needs, not how a given model would use them.
