# TASK-1011 — Full Industrial Device Behavior Library

Status: **DONE** (2026-10-12)
Linear: [ZFA-66](https://linear.app/recruit-verse/issue/ZFA-66)

Phase: **10 — Agent-Ready Engineering & Full Catalog Go Simulation**

## Objective
Implement reusable generic behavior models for the industrial categories represented by the Z-Factory catalog.

## Coverage
Drives/starters, motors, pumps/fans/conveyors/mixers/compressors, valves/actuators, relays/contactors/SSR, heaters, indicators/buzzers, switches/buttons, proximity/photoelectric sensors, process transmitters, encoders, controllers, remote I/O, IO-Link, converters/gateways and other catalog categories where behavior is meaningful.

## Acceptance criteria
- Every implemented behavior has deterministic tests.
- Command and actual feedback remain separate.
- Timing/ramping/travel/inertia is modeled where declared.
- Unsupported physics/vendor features are explicitly absent rather than invented.

## Prerequisites
- TASK-1009 (DONE): the runtime, its profile contract and the factory simulation in `services/process-sim/internal/device`.
- TASK-1010 (DONE): the behaviour contract (`lib/domain/behavior-contract.ts`), the parity test and every catalog model's simulation decision.

## Decisions (owner, 2026-10-11)
- **Go runtime only.** The new behaviours are implemented and tested in `services/process-sim/internal/device` and described in the behaviour contract; the server's TypeScript simulator is not extended. Until TASK-1015 switches factories to the runtime, catalog models of these categories stay `NOT_SIMULATABLE` with the reason that the runtime has the profile and the server simulator does not run it; the catalog refuses a `DEVICE_SIM` model on a profile the server does not run.
- **Scope: three groups, the protocol devices excluded.** Switching and thermal: `RELAY` (relay, contactor, solid-state relay), `HEATER`, `INDICATOR` (stack light, lamp, buzzer). Starters and servo: `SOFT_STARTER`, `MOTOR_STARTER` (direct-on-line starter with overload protection), `SERVO_DRIVE`, `SERVO_MOTOR`, `ENCODER`. Controllers and signal path: `PID_CONTROLLER` (process and temperature controllers), `SIGNAL_CONDITIONER`, `ACTUATOR` (pneumatic cylinder). Remote I/O, IO-Link masters, gateways, edge gateways and HMIs are protocol devices and belong to TASK-1013.
- **Delivered in two PRs** on one task, as TASK-1003 was: PR A the contract and runtime plumbing (new simulator types, the motor's supply from any starter, the step order) with the switching and thermal group; PR B the starters, servo, controllers and signal path.
- **Approximations stated, nothing invented.** Every profile's fidelity notes name its approximation and what is absent; no vendor physics, curves or parameters.

## Implementation — PR A (switching and thermal, and the plumbing)
- `services/process-sim/internal/device`: `relay.go` (RELAY: relay, contactor, solid-state relay), `heater.go` (HEATER), `indicator.go` (INDICATOR); `profile.go` gains the `Supply` interface and `SupplyState` (what a motor draws from a drive, relay or starter: energized, a frequency or the line, a speed limit while ramping); `motor.go` reads any supply through its `drive` link (`accepts` VFD and RELAY); `vfd.go` implements `Supply`; `simulation.go` orders a step as supplies, motors, loads, controllers, other actors, observers, validates the `contactor` link of a heater and accepts any supply as a motor's drive; `library_test.go`.
- `lib/domain/behavior-contract.ts`: the three profiles described; `runsOn` (server and runtime, or runtime only) on every profile; `BEHAVIOR_PROFILES` keyed by any simulator type; the motor's drive link accepts a relay; the heater's `contactor` link made from `CONTROLS`.
- Database: `SimulatorType` gains the library's types (`HEATER`, `INDICATOR`, `SOFT_STARTER`, `MOTOR_STARTER`, `SERVO_DRIVE`, `SERVO_MOTOR`, `ENCODER`, `PID_CONTROLLER`, `SIGNAL_CONDITIONER`, `ACTUATOR`), migration `20261011140000_simulator_types`; the `HEATER` and `INDICATOR` categories name their profiles.
- Catalog: a `DEVICE_SIM` model on a runtime-only profile is refused (`runsOn.server`); the generic contactor, heater and stack light are `NOT_SIMULATABLE` with the reason that the runtime models them and the server's simulator runs factories until TASK-1015.
- Tests: `library_test.go`, `behavior-contract.test.ts` (ported profiles apart from the library), `catalog.test.ts`, `device-parameters.test.ts`, `devices.test.ts`; the parity test lists the runtime's profiles from the contract.
- Docs: `docs/device-simulation.md` (The behaviour library), `docs/process-simulation.md`, `docs/device-catalog.md`, `docs/database.md`, `docs/testing.md`.

## Acceptance
- Every implemented behavior has deterministic tests: `library_test.go` covers each of the eleven profiles with fixed steps and no clock; the runtime's determinism test still holds.
- Command and actual feedback remain separate: every profile's signals are `IN` (commands, setpoints) or `OUT` (actual values, status), checked by the contract test; a controller's output is feedback the controlled device takes, never a PLC output.
- Timing/ramping/travel/inertia is modeled where declared: relay delays, heater time constant, flash rate, starter ramps, the overload relay's trip class, the servo profile's acceleration and deceleration, the cylinder's stroke times; each is a `TIMING` parameter of the contract.
- Unsupported physics/vendor features are explicitly absent rather than invented: every profile's `fidelity.notModelled` lists them and the docs repeat them; no vendor value appears anywhere.

## Remaining limitations
- The server's TypeScript simulator does not run the library; models of these categories are `NOT_SIMULATABLE` until TASK-1015, and the catalog refuses otherwise.
- Protocol devices (remote I/O, IO-Link master, gateways, edge gateway, HMI) are TASK-1013; no profile speaks a protocol yet.
- A motor starter is the only behaviour that raises a fault from its own physics; TASK-1014 generalises degraded states across the library.
- Position units of the servo profiles are generic; the catalog decides what a unit is (TASK-1012).
