# TASK-1009 — Go Catalog Simulation Runtime Foundation

Status: **DONE**
Linear: [ZFA-64](https://linear.app/recruit-verse/issue/ZFA-64)

Phase: **10 — Agent-Ready Engineering & Full Catalog Go Simulation**

## Objective
Expand the Go simulation service into a shared catalog-driven device runtime capable of hosting many industrial device instances and behavior models.

## Scope
- Deterministic tick engine for device behaviors.
- Factory/device isolation.
- Dynamic create/update/remove of simulated devices.
- Stable behavior-profile contract.
- Health, metrics and bounded resource usage.
- Preserve PLC-authoritative command/output semantics.

## Acceptance criteria
- The service can host heterogeneous device categories concurrently.
- Device behavior is selected from catalog simulation metadata rather than UI conditionals.
- One bad/slow model cannot stall unrelated device instances.

## Decisions (owner, 2026-10-11; ADR-0025)
- **Extend `services/process-sim` in place.** The catalog device runtime is the same Go service, binary, token, container and compose entry; device factories get an additive API family (`/v1/factories`, `/v1/profiles`) beside the untouched process-module contract. One service, many instances (ADR-0008).
- **Parity with the server's simulator first.** The ten generic behaviours of `lib/runtimes/device-sim` (VFD, motor, pump, fan, conveyor, mixer, compressor, valve, sensor, switch) are ported value for value with their signals, faults, links and approximations; TASK-1011 adds the catalog's other categories, TASK-1015 switches factories over. The server keeps its simulator until then.
- **Behaviour profiles are the contract.** Each profile describes itself (key, version, signals, faults, links, parameters, states, forcible); Z-Factory names a device's profile from the catalog's simulation metadata (`DEVICE_PROFILES`, by the category's `simulatorType`), not from the UI.
- **Isolation in the runtime, reported never silent.** One goroutine per factory; a behaviour that panics is `FAULTED`, one that overruns its step budget three times is `QUARANTINED`, both skipped with frozen outputs and BAD quality while the others go on; stalled factories are counted. Determinism holds for healthy devices.

## Implementation
- `services/process-sim/internal/device`: `profile.go` (the contract: `Signal`, `Fault`, `Link`, `Description`, `Behavior`, `Load`, `Forcible`, `Context`, the registry, parameter decoding that refuses unknown fields, the seeded mulberry32 generator), one file per profile (`vfd.go`, `motor.go`, `load.go` for pump and the generic loads, `valve.go`, `sensor.go`, `switch.go`), and `simulation.go`: the factory simulation (configs, links by role with the invariants `drive`, `one-motor-per-drive`, `motor`, `one-load-per-motor`, `measured-device`, `measured-signal`; the fixed step order actors then observers; trips and resets; inject, clear, reset, force; `Upsert` and `Remove` with rollback; a step per device under `recover` and a time budget; snapshots and events).
- `services/process-sim/internal/runtime`: the host of many factories (`Load`, `Unload`, `Inspect`, `List`, `Start`, `Stop`, `Reset`, `Step`, `Upsert`, `RemoveDevice`, `Device`, `SetInputs`, `InjectFault`, `ClearFault`, `ResetDevice`, `Force`, `Events`, `Metrics`, `Shutdown`); wall or manual clock per factory; 500 events per factory; 256 devices per factory and `PROCESS_SIM_MAX_DEVICES` (default 2048) over all; stall detection.
- `services/process-sim/internal/api/devices.go`: the routes, with the rule a refusal names in the problem body; `server.go` wires them, health gains `deviceContractVersion`, `factories`, `devices`, `profiles`, metrics gain `devices`; `cmd/process-sim/main.go` reads `PROCESS_SIM_MAX_DEVICES`.
- Server: `lib/domain/process-sim.ts` (`DEVICE_SIM_CONTRACT_VERSION`, the device types, `DEVICE_PROFILES`, health and metrics fields), `lib/runtimes/process-sim/client.ts` (`client.devices`, and the service's `rule` kept in the domain error), `lib/runtimes/process-sim/devices.ts` (`toDeviceSimDevices`: the server simulator's configuration as the runtime's devices).
- Tests: `internal/device/simulation_test.go` (the ported behaviour cases, dynamic devices, isolation of a panicking and a slow behaviour), `internal/runtime/runtime_test.go`, `internal/api/devices_test.go`, `lib/runtimes/process-sim/client.test.ts`, `lib/runtimes/process-sim/devices.test.ts`, and the parity and route checks in `test/integration/process-sim.test.ts` (`PROCESS_SIM_BIN`).
- Docs: ADR-0025, `docs/process-simulation.md` (Catalog device runtime), `docs/device-simulation.md`, `docs/architecture.md`, `docs/api-contract.md`, `docs/testing.md`, `docs/bootstrap.md`, `.env.example`, `compose.yaml`, `services/process-sim/README.md`, `docs/status.md`.

## Acceptance
- The service can host heterogeneous device categories concurrently: the runtime holds factories of drives, motors, pumps, loads, valves, sensors and switches at once; each factory ticks on its own goroutine; the runtime test steps one factory while another stays still, and the API test loads and runs a mixed factory.
- Device behavior is selected from catalog simulation metadata rather than UI conditionals: a device names its `profile`, which Z-Factory takes from `DEVICE_PROFILES` by the catalog category's `simulatorType` (`devices.test.ts` checks every simulated type has one); the service refuses an unknown profile or version.
- One bad/slow model cannot stall unrelated device instances: `TestABadOrSlowBehaviourDoesNotStallTheOthers` runs a panicking and a slow behaviour beside a drive chain; the chain's values are unchanged, the two are `FAULTED` and `QUARANTINED` with events, and configuring them again brings them back; factories are on separate goroutines, and a stalled factory is counted in the metrics.

## Remaining limitations
- Factories still run on the server's simulator; nothing in the product calls the runtime until TASK-1015. The parity test is the bridge between the two until then.
- A behaviour that never returns cannot be interrupted (Go cannot preempt it); the factory's tick stops and the runtime reports it as stalled. No shipped behaviour loops; the budget and quarantine cover slow ones.
- The profile descriptions name parameters by their defaults; the machine-readable schema with ranges and units is TASK-1010.
