# TASK-1108 — Expose Factory & Generate Edge Deployment JSON

Status: **PLANNED**

Phase: **11 — Multi-Protocol PLC Connectivity**

## Objective

Add an explicit **Expose Factory** workflow that validates the complete factory edge configuration and generates one versioned factory-level Edge Deployment JSON for the Industrial Edge Gateway Thin Client Agent.

The generated artifact is the authoritative deployment input for the Thin Client.

## User flow

```text
Factory Engineering
  -> configure PLCs/devices/tags
  -> select protocol per PLC
       - MODBUS_TCP
       - OPC_UA
  -> Expose Factory
  -> validate complete edge configuration
  -> generate Factory Edge Deployment JSON
  -> deploy/copy JSON to Industrial Edge Gateway
  -> Thin Client loads JSON
  -> create/update/remove PLC workers
  -> Modbus polling + OPC UA subscriptions
  -> normalized MQTT telemetry
  -> Web Factory
```

## Factory-level deployment contract

Generate **one deployment JSON per factory** containing all PLCs that are exposed through that edge deployment.

The document must include at minimum:

- schema version
- factory id / stable deployment id
- factory revision
- generated timestamp
- site/agent identity reference where applicable
- PLC collection
- per-PLC selected protocol
- protocol-specific connection details
- logical tag definitions
- protocol mappings
- read/write access metadata
- polling/subscription settings
- command/setpoint permissions
- configuration checksum/hash where appropriate

## Per-PLC protocol blocks

### MODBUS_TCP

Include only the data required by the Modbus worker, such as:

- host
- port
- unit id
- timeout
- polling interval
- register/coil mappings
- data type/encoding
- scaling where required

### OPC_UA

Include only the data required by the OPC UA worker, such as:

- endpoint URL
- security policy
- security mode
- authentication/certificate reference
- session/subscription settings
- explicit NodeIds
- data types
- read/write access

Secrets, passwords and private keys must never be exported as plaintext in the JSON. Use secure local references/configuration.

## Validation before exposure

`Expose Factory` must fail before producing an artifact if required deployment data is incomplete or invalid.

Examples:

- PLC has no selected supported edge protocol
- Modbus PLC has no host/port or no valid mapped registers
- OPC UA PLC has no endpoint
- OPC UA tag has no NodeId
- writable tag is not a COMMAND or SETPOINT
- duplicate logical tag ids
- incompatible/unsupported data type mapping
- factory contains unresolved engineering validation errors
- protocol selected is not supported by the PLC catalog/profile

Validation errors must be shown to the user and included in the page-level LLM Context in agent-readable form.

## Artifact lifecycle

- Every successful exposure creates a versioned deployment revision.
- Re-exposing after engineering changes creates a new revision.
- The user can identify the currently active/exported revision.
- The Thin Client can determine whether the configuration is new, unchanged or older.
- Hot reload must update only affected PLC workers.
- Removing a PLC from the exposed factory must cause the corresponding worker to stop after the new deployment is applied.
- Unchanged PLC workers should not be restarted unnecessarily.

## Thin Client behavior

On loading the factory deployment JSON:

1. validate schema and revision;
2. enumerate PLCs;
3. select the protocol adapter for each PLC;
4. validate the protocol mapping;
5. start/update/remove workers as required;
6. expose health per PLC;
7. publish normalized telemetry through MQTT;
8. preserve spool/replay behavior independently of the PLC protocol.

## Acceptance criteria

- Factory page exposes a clear **Expose Factory** action.
- One factory-level JSON contains all exposed PLCs for that factory.
- Mixed Modbus TCP and OPC UA PLCs are represented in the same document.
- Invalid protocol configuration blocks exposure with specific actionable errors.
- JSON is versioned and deterministic for the same engineering revision/configuration.
- Thin Client can load the document and instantiate the correct protocol worker per PLC.
- Re-exposure updates changed PLC workers without restarting unrelated workers.
- Removing an exposed PLC stops its worker after config activation.
- Writable mappings remain limited to approved command/setpoint roles.
- Existing PLC logic/interlocks remain authoritative for physical outputs.
- E2E test covers: engineer factory -> expose factory -> load JSON in Thin Client -> run one Modbus PLC and one OPC UA PLC -> publish normalized MQTT telemetry.
