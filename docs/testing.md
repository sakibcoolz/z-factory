# Testing Strategy

## Layers
- Unit: domain rules, mappings, codecs, validators, compatibility and simulator state machines.
- Component: compact/modular forms, peripheral picker, I/O occupancy, topology and export views.
- Integration: PostgreSQL/Prisma, Docker adapter, OpenPLC runtime, program deploy/reload, Modbus mapping, shared device simulator.
- End-to-end: factory creation -> PLC program execution -> device response -> live telemetry -> external Modbus command/readback -> PLC export.

## Mandatory high-risk tests
- Docker options cannot escape the allow-list.
- Port/subnet collisions.
- Compact/modular rack/module/I/O compatibility.
- Duplicate PLC endpoint assignment is rejected.
- Modbus address collisions and typed codec/byte-order behavior.
- Command/setpoint tags cannot be confused with feedback/status permissions.
- Gateway writes flow through PLC logic rather than directly mutating simulator state.
- VFD ramp/state/fault behavior and one-VFD-to-primary-motor invariant.
- Motor/pump/valve/sensor simulator state transitions.
- Runtime vs persisted-snapshot boundary.
- Runtime crash/disconnect/stale-value handling.
- External connectivity only through intended published ports.
- PLC export contains required engineering data and excludes secrets.

## End-to-end reference scenario
Pressure/level sensor -> OpenPLC logic -> VFD -> motor -> pump/process -> feedback tags; external edge gateway writes a setpoint/command and reads actual feedback; UI displays live state and an engineering export is generated.

### As automated (TASK-502)
`test/integration/e2e-demo.test.ts` runs this scenario against a real OpenPLC runtime (`TEST_DOCKER=1`): the pump station demo is built from the catalog and started as a factory; an edge client at the gateway endpoint writes the start command and the speed setpoint and reads actual frequency and pressure; the high-pressure interlock trips and is reset; a drive fault is injected and cleared; recorded commands, events, alarms and sampled telemetry are checked; the engineering export is produced; the factory is stopped. The manual version is `docs/demo-runbook.md`.

### The browser-agent proof (TASK-1008)
`test/browser-agent/browser-agent.test.ts` proves the agent-ready surface of Phase 10: a browser agent builds the reference design (a tank with its level transmitter and inlet valve, a pump on a motor and a drive, one compact PLC, every endpoint wired, the tank as a process module with its devices in their roles) through the normal UI only. The agent (`test/browser-agent/browser-agent.ts`) is a script, not a model, and that is the point: it starts at `/llm-index`, reads the parts and the areas from the DOM, follows the links the LLM Index and each page's LLM Context (`script[data-llm-context-json]`) offer, reads capacity and validation from the same JSON, asks the user every decision the context marks `confirm: required` (the test's user is a table of answers; an unknown question fails the run), applies an optional decision's default and records it, and reaches the server only through a real Chromium driven over the DevTools protocol (`test/browser-agent/cdp.ts`). It imports nothing of Z-Factory, and the first test checks that. The server is `next start` of the production build on the integration-test database (`test/browser-agent/app-server.ts`), so `npm run build` comes first. Gate: `TEST_BROWSER=1` (and `TEST_DATABASE_URL`); `CHROME_BIN` names the browser, else the one Playwright cached is used; `TEST_BROWSER_OUT` keeps a screenshot per page and the agent's `report.md`. The assertions: the index came first; every page the agent worked on had an LLM Context except the index and the factory form; the required decisions were asked with the page's choices and only the channel default was applied; capacity was confirmed before wiring; the designer, the factory overview and the I/O mapping report validation `ok`; the services see the same stored design with the module's roles filled; and the agent reports what the pages could not do: the module's two required signals cannot be bound, because every tag of the PLC carries a wired device signal and no page creates the program-driven (%M) tag a process signal needs. The run also found two gaps the task closed: connecting two devices was a drag only (the inspector gained Connect to), and the module editor's context asked for roles of other profiles.

## Definition of Done
Relevant tests pass locally/CI; new behavior has tests; failures and evidence are recorded in the task file.
