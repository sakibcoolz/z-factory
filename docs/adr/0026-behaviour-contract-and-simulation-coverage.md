# ADR-0026 — The Behaviour Contract and the Simulation Decision of Every Catalog Model

Status: **ACCEPTED** (TASK-1010, 2026-10-11)

## Context
ADR-0025 made behaviour profiles the contract between Z-Factory and the simulation service: a profile describes its signals, faults, links, parameters and states over the API, and a device's profile comes from the catalog's simulation metadata, never from the UI. Phase 10 asks for more: every catalog model must declare one coverage state (`FULL`, `PARTIAL`, `GENERIC`, `NOT_SIMULATABLE`), the catalog must refuse impossible or incomplete simulator metadata, generic and vendor facts must stay apart, and no vendor model may read as firmware emulation because its hardware is in the catalog. The contract existed in three places with no single statement: the TypeScript vocabulary (`DEVICE_SIGNALS`, `DEVICE_FAULTS`), the parameter forms (`device-parameters.ts`) and zod schemas (`params.ts`), and the Go descriptions.

## Decision
1. **One behaviour contract, in the domain.** `lib/domain/behavior-contract.ts` is the machine-readable description of every behaviour profile: commands and feedback (signals with direction, kind, unit and range), parameters (kind, unit, generic default, bounds, and a role: rating, timing, limit, initial, source, shape, event), states, faults with their reset rule and their effect on quality, links by role with the connection relationship they are made from and whether they are required, the protocol the profile speaks, whether a tester may force it, and its fidelity notes (approximations and what is not modelled). The parameter forms and the runtime's profile map are derived from it. The Go runtime describes the same facts (`parameterSchema` beside the defaults in `GET /v1/profiles`), enforces exactly the bounds it describes, and the parity test compares the two field by field, so the contract cannot drift from the code that runs it.
2. **Every catalog model declares its simulation.** The `simulation` block is mandatory: `NOT_SIMULATABLE` with the reason, or `GENERIC`, `PARTIAL` or `FULL` with the profile and version, the supported faults, parameter values and, for `PARTIAL` and `FULL`, the model-specific features Z-Factory declares and whether each is implemented. Coverage is a statement about a behaviour model; the catalog screen, its LLM Context and the coverage report say "a behaviour model, not vendor firmware" with it.
3. **The catalog refuses what is impossible or incomplete.** A model the device simulator executes (`runtimeSupport: DEVICE_SIM`) declares a profile, and only such a model does; the profile is the one of the model's category, at a version that exists; faults, parameter names and terminal signals are the profile's, and parameter values lie within its bounds; a terminal of a model that is not simulated names no simulator signal; `FULL` means every declared feature is implemented and `PARTIAL` means a mix.
4. **Generic and vendor facts stay apart.** A generic model is `GENERIC` or `NOT_SIMULATABLE`: it has nothing model-specific. A vendor model may run on the generic behaviour of its category with no claim; `PARTIAL` or `FULL` coverage, or any parameter value, is a model-specific fact that needs the model's `VERIFIED` provenance (TASK-1012 adds the per-fact source). A programmable controller is `NOT_SIMULATABLE` as a device: its program runs on the OpenPLC adapter, and no vendor firmware runs anywhere.
5. **Persisted and used.** `DeviceModel` carries `simulationCoverage`, `simulationProfile`, `simulationProfileVersion` and `simulationJson`; a model's parameter values become its model-level `SimulationProfile`, which the simulator already reads for every instance without values of its own.

## Consequences
- A new behaviour profile is one TypeScript description and one Go profile file; the parity test fails until they agree, and the catalog refuses a model that names a profile that does not exist.
- The shipped catalog is honest by construction: every generic model the simulator runs is `GENERIC`, every other model is `NOT_SIMULATABLE` with its reason, and nothing claims `PARTIAL` or `FULL` until TASK-1011 and TASK-1012 implement model-specific behaviour from authoritative sources.
- The coverage report of TASK-1016 reads the same columns and the same contract; it needs no second source.
- `docs/device-catalog.md` documents the block and its rules, `docs/device-simulation.md` the contract, `docs/database.md` the columns and the CHECK constraint.
- As built in TASK-1012: the per-fact source of decision 4 is the `sources` map of a vendor model's `simulation` block (one entry per parameter value, declared feature and supported fault, naming the document, the place and the approximation), resolved to its document when stored; a vendor model runs the generic profile of its category and never deploys firmware. `docs/device-catalog.md` → Vendor models on behaviour profiles.
