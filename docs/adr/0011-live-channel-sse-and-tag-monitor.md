# ADR 0011 — Live Channel: SSE, In-Process Tag Monitor and Replay by Event Order

Status: Accepted — 2026-10-05 (implemented in TASK-401; accepted by the owner)

## Context
ADR-0005 makes runtime memory the authority for live values and PostgreSQL the place for history. `docs/events-telemetry.md` names SSE as the first server-to-browser transport. TASK-401 had to decide three things those documents leave open:

- **Where live tag values come from.** The device simulator holds device state in memory, but nothing in the server knew the values a running PLC holds. The OpenPLC runtime (ADR-0009) does not push values; its Modbus server has to be asked.
- **What a browser gets after an interruption.** Recorded events must not be lost by a reconnect; tag values are not events and cannot be replayed.
- **In which order events exist.** Events were recorded by several services with unrelated ids. "Everything after the last event I saw" needs one order that storage and delivery share.

## Decision
1. **Tag monitor in the server process.** A module of the Next.js server (`lib/runtimes/tag-monitor/`) reads the tags of every PLC that has a started runtime, over the PLC's published Modbus endpoint, every `TAG_POLL_MS` (default 500 ms), with neighbouring addresses in one request. It only reads. Its memory holds the current value, quality and read time of each tag; nothing else in the server is asked for a live tag value. It follows ADR-0010: one object per process, no extra container or service.
2. **When a PLC is monitored.** While Z-Factory has a started runtime for it (a container, a Modbus endpoint, a state other than stopped, starting or stopping). Monitoring is brought in line with the stored state after every runtime operation and whenever a live screen or stream is opened, so it resumes by itself after a server restart. A PLC is no longer read before it is stopped on purpose.
3. **One recording path.** Every runtime event is recorded by `lib/services/event-service.ts`: it assigns the id and time, stores the event, applies the alarm rules, and publishes to the in-process bus. Recording is serialized per server process.
4. **Order.** Event ids are UUID version 7, generated by the server and strictly increasing within the process, with the time they encode as `occurredAt`. Storage order, id order and publication order are therefore the same.
5. **Transport.** `GET /factories/[factoryId]/stream` is a server-sent event stream with five message kinds: `event` (a recorded event, the only kind with an SSE `id`), `tags` (changed tag values of one PLC, plus a confirmation that the PLC answered), `snapshot` (the whole live state), `heartbeat` and `reset`. Commands do not use the stream; they stay server actions.
6. **Reconnect.** On every connect the server sends, in this order: the recorded events after `Last-Event-ID` (header, or `lastEventId` query for a stream the page opens anew), then a snapshot, then live messages. It subscribes before reading history and removes duplicates, so nothing recorded in between is lost or repeated. An id the factory does not have, or more than 500 missed events, yields `reset`: the client loads its lists again.
7. **Quality.** A value the monitor read is `GOOD`. When the PLC does not answer, the last value is kept and marked `DISCONNECTED`; a refused range is `BAD`. `STALE` is decided where the value is shown: a good value nobody has confirmed for longer than the stale time (at least 5 s, or four poll cycles), or any value while the stream is interrupted. A PLC that is not monitored has no value.
8. **Alarms.** An alarm is a condition with a beginning and an end (`AlarmEvent`), derived from recorded events by fixed rules: a simulated device fault, a failed PLC runtime, a PLC that stays unreachable, and a BOOL tag with role `ALARM` that the PLC program sets. Acknowledging is an operator action and never ends an alarm.
9. **Telemetry.** The monitor's hook stores a `TelemetrySample` for a tag when its value moved by at least the deadband (1 % of the last stored value, never less than the tag's resolution), not more often than the minimum interval, at least once per maximum interval, and on every change of quality. Samples and events are pruned by age.

## Consequences
- **Live values exist only while a PLC is monitored.** That is while it is started and this server process runs. Telemetry and PLC-raised alarms are recorded for the same period only. After a server restart nothing is recorded until a live screen or stream is opened, or a runtime operation runs.
- **One server process.** The bus, the monitor and the recording order live in process memory, like the simulator. Several server instances would each have their own; a shared bus and a shared sequence would be needed first, and need a new ADR.
- **Polling, not subscription.** A change shorter than the poll interval is not seen, and a value is up to one interval old. That is adequate for operating and observing a simulated plant, not for sequence-of-events analysis.
- **A second reader on the PLC.** The monitor and the simulator bridge both read the same Modbus endpoint. Each opens one connection per request.
- **Browser connection limit.** Over HTTP/1.1 a browser allows about six connections to one server, and each visible live page holds one for its stream. A hidden tab closes its stream and resumes when it is shown again; more than about five live pages visible at once would still block further requests. Serving through HTTP/2 removes the limit.
- **Alarm severity of PLC tags.** An `ALARM` tag raises a `WARNING` alarm: tags carry no severity or message yet. Per-tag alarm and telemetry settings need schema fields and are left to a later task.
- **Event history is finite.** Events and cleared alarms older than `EVENT_RETENTION_DAYS`, and samples older than `TELEMETRY_RETENTION_HOURS`, are deleted. Active alarms are kept.
- **WebSockets** stay unnecessary: the stream is one-way and commands are ordinary requests.
