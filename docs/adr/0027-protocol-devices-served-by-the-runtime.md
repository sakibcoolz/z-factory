# ADR-0027 — Protocol-Controlled Devices Are Served by the Runtime on Declared Register Maps

Status: **ACCEPTED** (TASK-1013, 2026-10-12)

## Context
Phase 10 asks for protocol-controlled devices: a drive the PLC commands over Modbus TCP instead of terminals, with register behaviour "where an authoritative Z-Factory mapping exists", mappings that are declared rather than guessed, and reads and writes that obey the behaviour model, its ranges and its write permissions. Three things existed: the behaviour profiles of the runtime (ADR-0025, ADR-0026), each a set of PLC-driven inputs and device-produced outputs; the server's Modbus TCP server for gateway endpoints (ADR-0013), which filters an external device's access to a PLC; and an unused `ProtocolRegisterDefinition` table at model level. The OpenPLC runtime also ships a Modbus master plugin, already used for PLC-to-PLC links (ADR-0016), so a PLC can poll a served device.

## Decision
1. **A register map is declared, in the contract.** `lib/domain/register-maps.ts` states, per map, the profile it exposes and every register: the signal, its area, address, data type, scale, offset, unit, access and role, and the engineering range a write must stay in. The area and the access follow from the signal's direction and kind (a command is a coil, a setpoint a holding register, boolean feedback a discrete input, numeric feedback an input register), so a map cannot expose feedback as writable; the rules are checked by the contract test, and the Go runtime declares the same map (`internal/device/registers.go`), validated against the profile at registration and compared field by field by the parity test. Z-Factory ships one generic map, the Modbus drive's (`VFD_MODBUS_TCP` v1). A vendor's map would be catalog data with its provenance, under the per-fact source rule of TASK-1012; none is declared, and the catalog refuses a model that names a map that is not declared.
2. **The runtime serves the maps.** A factory with protocol devices carries a `modbusTcp` listener in its configuration; the runtime opens one Modbus TCP listener per such factory (`internal/modbus`, standard library only) on its configured bind address and port range, and every protocol device answers at its unit id with exactly the registers of its map. A read gives the device's commands as last written and its feedback as the behaviour produced it, scaled to raw words; a write sets the behaviour's inputs, only on a writable register and within the signal's range, resolved against the device's effective parameters. Everything else answers a Modbus exception before the device is touched: an unmapped address or a write to a read-only register `02`, a value outside the range `03`, an unknown unit id `0A`. A write touching several registers is applied whole or not at all. Writes are events (`PROTOCOL_WRITE` per changed signal, `PROTOCOL_WRITE_REJECTED` at most once per address every 30 seconds).
3. **The behaviour does not change.** A served device runs the same profile as a hardwired one: the Modbus drive is the VFD profile behind a map. A write over Modbus and a PLC output wired to a terminal land on the same input; the PLC remains the control authority, and the runtime never writes a PLC output.
4. **The catalog names the map.** A model's simulation block carries `protocol` (kind, map, version); a model the server's simulator does not run names in `runtimeOnly` the profile and protocol the runtime would run for it, so TASK-1015 can switch it over by data. The import writes a model's map into `ProtocolRegisterDefinition`, and the catalog screen and the LLM Context show it. A model served over a protocol has a communication port for it.
5. **Adapters stay extensible.** A map's `protocol` is a kind; the runtime's listener, the catalog's rule and the client types are keyed by it. Modbus TCP is the one kind today.

## Consequences
- The device side of a Modbus drive exists and is proven against a client: a factory loaded into the runtime serves it, and the parity test holds the map in the contract and the runtime together.
- Reaching a served device from a PLC container is not done: the runtime listens on the host's loopback by default, PLC containers live on factory networks, and the PLC's Modbus master configuration names only PLC links. TASK-1015, which moves factories to the runtime, decides the network path (a bind address the factory network can reach, or the runtime on the factory network) and configures the PLC's master for the device. Until then the Modbus drive stays `NOT_SIMULATABLE` in the catalog with that reason.
- No remote I/O profile exists: a remote I/O station exposes channels, not a behaviour, and needs a profile of its own with the wiring rules of PLC channels. The catalog says so on the model.
- The runtime's listeners have no authentication, like every Modbus TCP server; they bind to one address of the operator's choice (`PROCESS_SIM_MODBUS_BIND`, default loopback) and a port range (`PROCESS_SIM_MODBUS_PORTS`), and serve only declared registers. `docs/security.md` records the limit.
